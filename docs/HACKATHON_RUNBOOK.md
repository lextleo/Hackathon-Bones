# Hackathon runbook

A practical default rhythm. Adjust it to the event length and team size.

## First 10% — align

- [ ] Read the rules, required deliverables, judging rubric, and submission deadline.
- [ ] Pick one target user and one problem.
- [ ] Write the one-line pitch and demo promise in `PROJECT_BRIEF.md`.
- [ ] Decide the smallest end-to-end path and explicitly cut the rest.
- [ ] Assign clear owners and agree on component contracts.

## Next 20% — prove the path

- [ ] Scaffold only the required components.
- [ ] Make one realistic happy path work with stubs or sample data.
- [ ] Commit a run command and setup notes.
- [ ] Test the riskiest dependency early: hardware, data access, API quota, model latency, or deployment.

## Middle 45% — build and integrate

- [ ] Work in small, mergeable slices.
- [ ] Keep `main` usable and integrate frequently.
- [ ] Test interfaces before polishing visuals.
- [ ] Capture evidence for any performance or impact claim.
- [ ] Keep a short list of blockers and cut scope when needed.

## Final 25% — freeze and tell the story

- [ ] Stop starting new features; fix the demo path.
- [ ] Run from a clean restart on the actual presentation machine.
- [ ] Test the fallback clip / screenshots.
- [ ] Finish slides and pitch notes.
- [ ] Check repository hygiene, setup instructions, secrets, and submission requirements.
- [ ] Submit before the last minute; leave time for upload or form issues.
