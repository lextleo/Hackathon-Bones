# Contributing

Hackathon work moves quickly. Keep contributions small, testable, and easy for another teammate to understand.

## Before opening a pull request

- Explain the user problem or technical reason for the change.
- Keep the change focused; split unrelated cleanup into another pull request.
- Test the main path and mention what you tested.
- Update setup instructions, API contracts, or screenshots when behaviour changes.
- Remove secrets, private data, generated build output, and local-only files.

## Suggested branch names

- `feat/short-description`
- `fix/short-description`
- `docs/short-description`
- `chore/short-description`

## Commit messages

Prefer short, action-oriented messages such as `feat: add sensor status panel` or `fix: handle missing device data`. Use the team's convention if one exists.

## Team agreement

Pick an owner for each critical path, agree on the interface before parallel work, and integrate early. A working end-to-end demo is more valuable than several disconnected components.
